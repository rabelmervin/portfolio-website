# Entities

## 1. What it is and Purpose
The **Entities** component is where the GraphQL API is actually born. It is a WebAssembly component (`wasm32-wasip2`) that holds the compiled SeaORM entity structs generated by Kompilre and uses [Seaography](https://www.sea-ql.org/Seaography/) to auto-generate a complete GraphQL schema.

Its purpose is to be a **pure, schema-aware GraphQL executor** . By isolating all database schema knowledge into this single component, Graphily achieves zero-downtime schema updates — when the DB schema changes, only the Entities component is hot-swapped.

## 2. Component Boundaries (The WIT Contract)
This is the most critical section for any Wasm component. Other engineers need to know exactly how to talk to it.

**Exports (Provides)**
- `graphily:entities/entities-api` (Exposes `execute(GqlRequest)` and `entity_names()`)

**Imports (Requires)**
- `graphily:mysql/mysql-api` (The MySQL host plugin for executing the SeaORM queries generated by Seaography)

## 3. Core Responsibilities
- **Schema Generation**: Builds a full GraphQL schema from SeaORM models with extensive customizations to match BettyQL naming conventions (`where`, `sort`, `results`).
- **WIT MySQL Proxy**: Implements `ProxyDatabaseTrait` to route SeaORM SQL queries through the WIT boundary to the host plugin.
- **RBAC & Row-Level Security (Lifecycle Hooks)**: Uses Seaography hooks to enforce data-level security during SQL generation:
  - **Entity Guard**: Blocks unauthorized nested relation access based on the access matrices.
  - **Field Guard**: Hard-blocks read access to sensitive internal fields (like `password`, `cas_token`) at the SQL level.
  - **Row-Level Security**: Dynamically injects `WHERE {column} = {user_id}` for configured entities.
  - **Permission Filters**: Translates access matrix rules into dynamic `WHERE` conditions, replacing `$user_id` and `$user.<path>` with JWT claims.
  - **Table Lenses**: Applies per-entity lens filters for read operations.
  - **Non-native Filter Extension**: Merges `GraphilyFilterExt` (OR / non-native filters) into the SQL condition.

## 4. Internal Data Flow
1. **Receive Request**: Accept a `GqlRequest` (query, variables, operation-name, db-url, `SecurityContext`).
2. **Attach Context**: Deserialize `SecurityContext` into the request; pull `__graphilyExt` from variables into `GraphilyFilterExt`.
3. **Execute Schema**: Run the Seaography schema; lifecycle hooks enforce entity/field guards, row-level security, lenses, and permission filters.
4. **Execute over WIT**: SeaORM uses `WitProxy` to call MySQL via the WIT host plugin.
5. **Serialize**: Return the GraphQL JSON response back to Data-Engine.

## 5. Libraries / Crates Used
| Crate | What it does in Entities |
|---|---|
| **`sea-orm`** | Core ORM providing entity models and the `ProxyDatabaseTrait` capability. |
| **`seaography`** | GraphQL schema generator and query engine with LifecycleHooks. |
| **`wit-bindgen`** | Generates WIT bindings for cross-component communication. |
| **`serde` / `serde_json`** | Serialization of the SecurityContext and GraphQL responses. |
| **`chrono`** | Date/time parsing from MySQL string results. |
| **`once_cell`** | Lazy initialization of the global compiled GraphQL schema singleton. |
| **`entities-macros`** | Local proc-macro crate to auto-register BettyQL custom types at compile-time. |
